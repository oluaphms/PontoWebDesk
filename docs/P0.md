# P0 — Pilot Ready (pré-requisito clientes pagantes)

**Prioridade:** máxima  
**Pré-condição:** ambientes organizados (`docs/environments.md`); limpeza técnica já feita  
**Esta fase NÃO está implementada** — apenas planejada

## Objetivo

Tornar o produto **apto a piloto controlado** (1–20 empresas) com risco multi-tenant, ingestão REP e recuperação de dados sob controle operacional.

## Impacto

| Área | Ganho |
|------|--------|
| Segurança / multi-tenant | Defesa em profundidade no Postgres; menos superfície de vazamento |
| Estabilidade REP | HTTP de ingest não espera promote/recalc |
| Continuidade | RPO/RTO reais e testados (não só export JSON) |
| Confiança comercial | Claims honestos para piloto (sem “enterprise certificado”) |

## Risco

| Item | Risco de execução | Mitigação |
|------|-------------------|-----------|
| RLS fail-closed | Bloqueio de leituras se `set_config` falhar | Staging primeiro; smoke cross-tenant; rollback de flag |
| Flags prod | Regressão em escritas genéricas / bridge REP | Inventário de callers antes; feature flag |
| Async REP | Folha atrasada vs sync | Métricas de fila pending; fallback sync documentado |
| Backup | Restore mal testado | Drill obrigatório antes de go-live piloto |

## Itens (ordem de execução)

### P0.1 — RLS VPS fail-closed
- Corrigir política `ELSE true` → deny quando `app.current_company_id` vazio
- Aplicar `016_vps_rls_tenant_isolation.sql`
- `VPS_RLS_ENFORCED=true` em produção após smoke

### P0.2 — Flags de superfície segura em produção
- `DATA_API_WRITES_ENABLED=false`
- `REP_BRIDGE_LEGACY_ENABLED=false`
- Redis/Upstash rate-limit ativo (`RATE_LIMIT_REDIS_REQUIRED=true`)

### P0.3 — `REP_POST_INGEST_ASYNC=1`
- Staging → produção
- Observar pending / falhas de promote

### P0.4 — Backup Postgres automatizado + restore drill
- Cron/`pg_dump` ou WAL offsite
- Documentar RPO/RTO reais
- 1 restore drill com evidência

### P0.5 — Congelar dual-stack no path do piloto
- Inventário do que ainda usa `api/*` Supabase service role
- Desabilitar ou isolar do tráfego de clientes piloto
- Path canônico: `LOCAL_API` → VPS

## Dependências

- Acesso VPS + Postgres + Redis/Upstash
- Staging (ou tenant piloto isolado) para smoke RLS
- Janela de manutenção curta para restore drill
- Decisão comercial: piloto ≠ claims SOC/ISO

## Critério de aceite

- [ ] `VPS_RLS_ENFORCED=true` em prod; token empresa A **não** lê dados B
- [ ] Login, `/api/employees`, batida REP, `/api/data/time_records` OK pós-RLS
- [ ] Writes genéricas off; bridge legado off; rate-limit Redis OK
- [ ] Async REP ligado; sem timeout sistemático no ingest sob carga sintética
- [ ] Backup automático rodando; restore drill documentado (data, tempo, responsável)
- [ ] Inventário dual-stack fechado; piloto só no path LOCAL_API/VPS

## Rollback

| Item | Rollback |
|------|----------|
| RLS | `VPS_RLS_ENFORCED=false` + restart API; investigar `set_config` |
| Flags | Reverter env na VPS + `pm2 restart` |
| Async REP | `REP_POST_INGEST_ASYNC=0` |
| Backup | Não reverte dados; manter último dump bom |
| Dual-stack | Reabilitar handler legado só se inventário exigir |
