# P0.2 — Relatório Path Único de Acesso a Dados

## Fluxo oficial (mantido)

```
Frontend → API Express (/api) → PostgreSQL VPS
```

Provider padrão: `VITE_DATA_PROVIDER=LOCAL_API`.

## Acessos encontrados

| Tipo | Onde | Classificação |
|------|------|----------------|
| HTTP `/api/data`, `/api/employees`, etc. | `src/services/dbHttp.ts`, `src/services/api.ts` | **Canônico** |
| Import `supabaseClient` / `db` | Dezenas de pages/services | **Facade** — `services/supabaseClient.ts` re-exporta `dbHttp` (não é PostgREST) |
| `getSupabaseClient()` | `src/lib/supabaseClient.ts` | **Stub** — lança erro (acesso direto bloqueado) |
| Vercel `api/*` + service role | `api/**` | **Legado dual-path** — fora do piloto LOCAL_API |
| Jobs FE → `/jobs/*` | `adminCalcPeriodJob.service.ts` | Pode ir à Vercel se URL apontar para lá — **exceção operacional** |
| Realtime `.channel()` | `src/pages/RealTimeInsights.tsx` | Só se `isSupabaseConfigured()`; em LOCAL_API tipicamente **não executa** |
| Auth recovery Supabase | Backend `SUPABASE_URL`/`ANON` | **Exceção justificada** (recovery password) |
| Agente / scripts Node | `services/sync*.js`, agente | Edge / offline — fora do browser |

## Acessos removidos nesta fase

**Nenhum** caminho funcional do FE LOCAL_API foi removido.

Motivo: a unificação já ocorreu via facade `dbHttp`. Remover imports `db`/`supabaseClient` ou o bloco Realtime de `RealTimeInsights` **alteraria código de UI** sem ganho runtime no path oficial e violaria “não alterar comportamento do frontend”.

## Exceções mantidas (justificadas)

1. **Nome legado `supabaseClient`** — facade HTTP; renomeação massiva = risco sem benefício P0.
2. **`api/*` Vercel** — isolamento operacional do piloto (desligar no deploy), não delete de código nesta fase.
3. **Supabase Auth recovery** — backend only.
4. **Realtime Insights** — morto se LOCAL_API; manter código para não mudar UX se flag cloud existir.
5. **REP agent / offline queues** — processos edge.

## Conclusão

Path único **já é o padrão de runtime** para o app em LOCAL_API. P0.2 fecha o inventário e documenta exceções; remoção agressiva de dual-stack fica para aceite operacional (checklist P0.5) sem reescrever o FE.
